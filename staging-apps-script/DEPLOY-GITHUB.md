# GitHub Actions deployment — STAGING only

1. Enable Apps Script API at https://script.google.com/home/usersettings while signed in to the dedicated STAGING Google account.
2. Use the new standalone project at https://script.google.com/create named exactly **BM FUEL STAGING - GitHub**. Do not reuse or rename an existing production or bound script. Copy its Script ID from Project Settings. The web app code opens only the approved STAGING spreadsheet (ID ending 8RHry0hU).
3. In a trusted local terminal with Node.js 22+, run `npx @google/clasp@3.4.1 login` using the dedicated STAGING account only. This creates ~/.clasprc.json. Never paste it into chat, commit it, or upload it to a public site.
4. GitHub repository Settings > Environments > New environment: **bm-fuel-staging**. Restrict deployment branches to **staging-google-apps-script-meter**. Add environment secrets **BM_STAGING_SCRIPT_ID** (from step 2), **BM_STAGING_CLASPRC_JSON** (the entire local clasp 3.x auth file from step 3). Do not use production credentials. Set required reviewer if available.
5. Trigger a new push to the staging branch changing this directory (or rerun the failed setup job). The workflow does not run on main; manual workflow dispatch may not appear because the workflow is not on the default branch. Do not merge it to main just to run.
6. Read the successful deployment output and open its /exec URL while signed into the deploying Google account. Approve Sheets scope if Google prompts. Confirm exactly six fictional rows in Meter_Log and repeat date to verify duplicate rejection. No real sales.
7. If deployment succeeds but no Web App URL is created, open Apps Script Deploy > Manage deployments and create a Web app manually, Execute as Me, Who has access Only myself. Do not enable public access. Review any existing deployment before rerunning the workflow.

The workflow verifies the remote project name, exact configured standalone script ID, absence of a parent, local STAGING spreadsheet guard, code footprint, and existing deployment marker before clasp push. All credentials stay on the ephemeral runner. It never runs Railway or writes production. It intentionally fails if secrets are absent; this is not evidence of a deployed web app. Only owner access for now, not staff accounts or the full dashboard.
